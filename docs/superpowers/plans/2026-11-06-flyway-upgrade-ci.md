# Flyway 기존 DB 업그레이드 CI 검증

## 범위와 선택

사용자 요청: CI에서 기존 DB 업그레이드를 검증한다. 기존 `backend` 필수 체크에 별도 Gradle 테스트 작업을 추가하며 프런트엔드·서비스 코드·마이그레이션·운영 DB는 변경하지 않는다.

추적 이슈: https://github.com/ync-capstone-desgin/hkagri-supplier/issues/41

PR은 대상 브랜치 SHA, develop/main 푸시는 직전 SHA의 마이그레이션을 추출한다. 같은 Flyway/PostgreSQL 버전으로 기준 스키마와 가상 업체 1건을 만든 뒤 현재 코드의 마이그레이션을 적용하고 기록 보존을 확인한다. 기존 파일 수정·삭제와 뒤늦은 낮은 버전은 실패시킨다. 기준 파일을 찾지 못해도 검사를 생략하지 않고 실패한다.

기존 Testcontainers와 JUnit을 재사용한다. 일반 `test`와 구분한 `migrationUpgradeTest`를 CI가 함께 실행한다. 새 필수 체크 이름이나 의존성은 추가하지 않는다. 브랜치 갱신 전의 통과 결과와 실제 운영 데이터 전체를 검증하는 것은 범위 밖이다.

## 실행과 검증

1. 업그레이드 테스트와 순서 역전·체크섬 변경·마지막 적용 파일 삭제 회귀 사례를 추가한다 → 실제 PostgreSQL에서 의도한 실패/성공 확인.
2. 기준 마이그레이션 추출과 Gradle 작업을 CI에 연결한다 → V7→V8 및 현재 develop 기준 검증, 기준 파일 누락 시 실패 확인.
3. 실행 방법·적용 순서 주의를 문서화한다 → 변경 파일 검토, 전체 백엔드 테스트와 업그레이드 테스트.
4. 별도 커밋·드래프트 PR을 만들고 backend/frontend CI를 확인한다. 병합은 하지 않는다.

## 로컬 검증 결과

- 기본 Flyway 설정에서 최고 적용 버전 파일 삭제를 놓치는 실패를 재현했다. CI 전용 무시 패턴을 비운 뒤 회귀 사례 3개와 실제 V7→V8 업그레이드가 모두 통과했다.
- 기준 폴더를 전달하지 않은 실행은 안내 메시지와 함께 실패했다. 워크플로의 실제 추출 명령도 V8 파일 8개 추출 성공·없는 기준 커밋 거절을 확인했다.
- CI와 같은 명령으로 현재 develop(V8) 기준 일반 테스트 92개와 업그레이드 테스트 4개가 실패·오류·누락 없이 통과했다.
- YAML 파싱과 `git diff --check`를 확인했다. 서비스 마이그레이션과 #14 미리보기 서버는 변경하지 않았다. 원격 실행 결과는 연결한 PR의 CI 체크에서 확인한다.
